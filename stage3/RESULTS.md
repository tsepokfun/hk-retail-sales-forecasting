## 1. 為什麼要做這一階段

`01_ARCHITECTURE.md` §5 的新聞融合設計與 §7 消融表的第 4、7、8 項要求回答兩件事：

1. **文本資訊本身**能不能提升月度零售多步預測？
2. **xLSTM 骨幹本身**是否值得，還是傳統 LSTM 就夠？

這一階段的設計原則是**事前登記判準（pre-registered decision rule）**：
一個文本 cell 只有在**贏過同寬度噪音對照**時，才可宣稱帶有資訊。
只贏過 `none` 不算 —— 因為 `none` 的寬度是 0，任何「贏」都可能只是欄位數不同。

## 2. 資料層：GovHK 新聞標題

### 2.1 為什麼只取標題

每日歸檔頁本身就是一行一篇的新聞清單，而那一行就是政府在用自己的措辭描述事件
（例如 "Retail sales up 3.2 per cent in December"）。抓 10 萬篇內文會令請求量增加約 30 倍、
耗時數小時，而相對標題幾乎沒有額外訊號。**這是明確記錄下來的範圍決策，不是取巧。**

### 2.2 抓取設計與規模

| 項目 | 內容 |
|---|---|
| 端點 | `https://www.info.gov.hk/gia/general/YYYYMM/DD.htm` |
| 範圍 | 2004-10 → 2024-12（243 個月） |
| 抽樣 | 每月固定 7 天（1/5/10/15/20/25/28），**保持月度可比** |
| 實測產出 | **42,594 條標題 / 226 個有新聞的月份** |
| 耗時 | **178 秒**（6 執行緒、timeout 10s、3 次重試） |
| 快取 | 每月一個 JSON（`data/news_cache/YYYYMM.json`），重跑零成本、可續跑 |

**三段式 markup 相容**（全部實測，不是假設）：

```
2004–2007   <a href="05/1105198.htm">Title</a>
2008–2016   <a href="http://www.info.gov.hk/gia/general/...">Title</a>
2017–2024   <a class="NEW" href="/gia/general/YYYYMM/DD/P....htm">Title</a>
```

用 href 形狀（而非黑名單）區分新聞稿與周邊 chrome（字級切換、sitemap、語言切換）。

### 2.3 覆蓋率（實測，不是假設）

| 年份 | 有新聞的月份 / 總月份 | 標題數 |
|---|---|---|
| 2004 | 3 / 3 | 515 |
| 2005 | 8 / 8 | 1,036 |
| 2006 | 4 / 4 | 117 |
| 2007 | 7 / 7 | 719 |
| 2008–2024 | **每年 12 / 12** | 2,068 – 3,218 |

⚠️ **2005–2007 只有部分月份可機械解析**（該年代頁面由 inline script 生成，抓不到 anchor）。
**37 個月無覆蓋 → 以訓練期均值填補（z = 0）**，而非填 0 ——
填 0 會錯誤宣稱「當月沒有新聞發生」。

### 2.4 兩種表示法

| 特徵 | 定義 | 欄數 |
|---|---|---|
| `news_log_count` | `log1p(當月標題數)` | 1 |
| `news_fin_share` | 命中 `retail\|sales\|consum\|touris\|visitor\|inflation\|price\|econom\|rate\|tax\|voucher\|epidemic\|covid\|...` 的標題佔比 | 1 |
| `news_sent_net` | `(正向詞 − 負向詞) / (正向詞 + 負向詞)`，手寫詞典 | 1 |
| `news_pc1..4` | `sentence-transformers/all-MiniLM-L6-v2` 逐條編碼 → 月度平均 → **train-only PCA(4)** | 4 |

**實測 PCA 解釋變異比** `[0.2388, 0.0847, 0.0672, 0.0450]`（合計 **0.436**）。

**對齊規則**：月份 `t` 的特徵只用**發布日期落在 t 月內**的標題，並採 `shift(0)` ——
因為當月標題在月底前已全部發布，在原點 `t` 是已知的。這與 Stage 1 對 HKO 氣象的處理一致
（`EXOG.md` 判斷 J8）。

## 3. 因果驗證（三項）

### 3.1 結果

| 檢驗 | 問題 | 結果 |
|---|---|---|
| **Q1 公式** | 每欄是否等於文件所寫的轉換？ | **3/3 PASS**，最大絕對差 **4.4e-16** |
| **Q2 因果性** | 有沒有任何一格偷看未來？ | **7/7 PASS**，窗口內差值 **0.0（位元級相同）** |
| **Q3 缺失政策** | 無覆蓋月是否填成訓練均值？ | **PASS**（37 個月的 z 值全部恰為 0） |

**Q2 的做法**：刪掉所有 `month > 202312` 的標題（實測保留 40,126 / 42,594 條），
**連 scaler、PCA 一起重建**，再比對 `≤ 202312` 的 231 個月。
若管線裡有全樣本 PCA、全樣本 z-score 或漏掉的 shift，這裡就會出現非零差。

### 3.2 🔴 Q2 第一次跑是 FAIL，而它抓到的不是模型問題

第一次跑 Q2 時 7 欄全部 FAIL，差值高達 0.91–1.26。原因不是洩漏，而是：

```python
masked = d[d["date"] <= TRAIN_END]      # "20231231" <= "202312"
```

8 字元的日期 `"20231231"` 與 6 字元的月份 `"202312"` 做**字串比較**時是**前綴比較** ——
`"202312"` 是 `"20231231"` 的前綴，所以 `"20231231" > "202312"`，於是**整個 2023 年 12 月被誤刪**，
令 z-score 的 μ/σ 全部位移，所有欄都「看起來洩漏了」。

改成比較 `month` 欄之後，7 欄差值全部變成 **0.0**。

> **這正是前綴遮罩測試存在的意義**：它不只抓模型洩漏，也抓資料處理錯誤。
> 一個「FAIL」如果被當成「有洩漏」而去改模型，就會往完全錯誤的方向修。

## 4. 消融設計

所有 cell 皆 `purge_val=True`、100 epochs、三種子 42 / 7 / 2024。

| cell | 欄數 | 內容 | 同寬度噪音對照 |
|---|---|---|---|
| `none` | 0 | 無外生（Stage-1 結果） | —— |
| `text_scalar` | 3 | 詞典／計數 | `random3`（Stage-1，已存在） |
| `text_emb` | 4 | MiniLM + PCA | `random4`（本階段新增） |
| `visitor_mtr_text` | 6 | `visitor_yoy` + `mtr_yoy` + 4 個 PCA | `random6`（本階段新增） |
| `LSTM_none` | 0 | **傳統 `nn.LSTM` 骨幹** | —— |
| `LSTM_text_emb` | 4 | LSTM 骨幹 + 4 個 PCA | —— |
| `none_k6` | 0 | k=6 驗證視窗 | —— |
| `visitor_mtr_k6` | 2 | k=6 驗證視窗 + 人流 | —— |

### 4.1 骨幹對照的公平性

`stage3/lstm_backbone.py` 的 `LSTMForecaster` **直接繼承** `XLSTMForecaster`，
只覆寫 `_backbone`：

```
xLSTM : xLSTMBlockStack(2 blocks, mLSTM×1 + sLSTM×1, embed=32)
LSTM  : nn.LSTM(input_size=32, hidden_size=32, num_layers=2,
                batch_first=True, dropout=0.3)   → 取最後一層輸出
```

輸入投影、序列嵌入、**可學習持久性／季節性錨點**、四個輸出頭、loss、優化器、schedule、
early-stopping **全部不動**。否則「xLSTM vs LSTM」會同時改變兩件事。

**自測實測**（`python -m stage3.lstm_backbone`，CPU，2 秒）：

```
P1_film_lstm_epoch0_identical      True
P2_film_lstm_branch_trainable      True
n_params_xLSTM_backbone            19920
n_params_LSTM_backbone             19272
n_params_LSTM_FiLM                 20488
PASS                               True
```

| 對比 | h | DM | p | 判讀 |
|---|---|---|---|---|

### 5.5 三個值得注意的細節

1. **文本在 h=12 反而有幫助。** `text_scalar` 的 h=12 MASE 是 **0.85268**，**低於基準 0.86294**
   與同寬度噪音 0.90028；`text_emb` 的 h=12（0.91653）也低於它的噪音對照（0.94961）。
   但在 h=1 與 h=6 崩壞（`text_scalar` h=6 1.47602 vs 噪音 1.19564）。
   → **新聞文字抓的是體制／水平轉變，對「一年後」有用，對「下個月」只是雜訊。**
   淨效果（ALL）仍然是大幅變差。
2. **嵌入法明顯優於詞典法**（`text_emb` 比 `text_scalar` 好 **8.84%**）。
   手寫的關鍵詞表與情緒詞典丟失了太多語意，MiniLM 的句向量保留得更多。
3. **`LSTM_text_emb` 是全部 12 個 cell 中最差的一組（1.34041）**，比 `LSTM_none` 差 27.50%。
   同一份文本在 LSTM 上的破壞力比在 xLSTM 上更大（xLSTM：`text_emb` 1.08961 vs `none` 0.98355 = +10.8%）。

### 5.6 結論（可寫進報告）

> **新聞文本在這個架構上沒有可偵測的增量價值，三種表示法全部輸給同寬度噪音。**
>
> 但有一個**方向性的例外**：文本在 **h=12** 上是有用的（`text_scalar` 0.85268 < 基準 0.86294），
> 只是在 h=1/h=6 的傷害更大，令總分變差。
>
> **xLSTM 骨幹本身值得**：傳統 2 層 `nn.LSTM` 在同樣的輸入投影、錨點、loss、訓練迴圈下
> 差 **+6.89%**，且 h=12 的差距統計顯著（p=0.000818）。

## 6. `purge_val` 視窗敏感度（k = 6）

**動機**：出貨協定是 `val_from = cutoff − 24` 之後再 purge，結果**丟掉 2023 整年 12 個原點**，
訓練只到 2021-11（見 `stage1/RESULTS.md` §7.8 解釋 2）。把驗證改成「最後 k 個合法原點」，
訓練就能推進到 2022-06。

```
k = 6  →  驗證原點 2022-07 .. 2022-12（6 原點 = 138 樣本）
          訓練原點 2006-10 .. 2022-06（比出貨協定多 7 個原點 = 161 個樣本）
          最大驗證標籤 = 2023-12（仍然 100% 不碰 2024）
```

### 6.1 結果

| cell | h=1 | h=3 | h=6 | h=12 | **ALL** | 相對基準 |
|---|---|---|---|---|---|---|
| `none`（出貨協定） | 0.89161 | 1.07002 | 1.10963 | **0.86294** | 0.98355 | —— |
| **`none_k6`** | 0.90107 | **1.03921** | **1.09658** | 0.87270 | **0.97739** | **−0.63%** |
| `visitor_mtr`（出貨協定） | 0.95344 | 1.08675 | 1.13258 | 0.87541 | 1.01204 | +2.90% |
| `visitor_mtr_k6` | 0.95160 | 1.08953 | 1.12600 | 0.89762 | 1.01619 | +3.97% |

**逐種子（ALL）**：`none_k6` = 1.01528 / **0.95578** / **0.96111**；
`none` = 0.95989 / 1.01743 / 0.97333 → seed 42 與 2024 明顯改善，seed 7 變差。

### 6.2 判讀（誠實、不單邊）

**`none_k6` 整體好 0.63%，但這不是全面勝利：**

- **h=1 / h=3 / h=6 三個視界都改善**（1.10963 → 1.09658 等），
- **但 h=12 變差且統計顯著**（0.86294 → 0.87270，DM p=0.0317），
- **逐種子不一致**（2 好 1 壞），
- 而 `visitor_mtr_k6` 相對 `none_k6` 仍然差 3.97% —— **人流變數在 k=6 協定下依然沒有幫助**。

> **結論**：出貨協定的 `val_months=24` 確實丟掉了 7 個可用的訓練原點（2022-01..2022-06），
> 把它們拿回來對短視界有幫助、對 h=12 有害。**這是一個需要按視界取捨的協定參數，
> 不是一個「越長越好」的常數。**
> 由於幅度只有 0.63% 且逐種子不一致，**本專案不建議在最終模型採用 k=6**，
> 但應在 limitations 中記錄：`val_months=24` 不是最優選擇。
